## **Core Principles**

* **「実装の速さ」と「品質の安定」を両立せよ。**
* **「何が書けるか」ではなく「どの観点で書くべきか」を最優先せよ。**
* **正常系中心の薄いテストを禁止し、QA技法に基づいた多角的な検証を行え。**

## **Test Design Skills**

### **1. 観点の網羅とQA技法の適用**

テストケースの抽出には以下の技法を必ず適用せよ。

* **同値分割（Equivalence Partitioning）：** 入力値をグループ化し、無駄な重複を排除した代表値を選定せよ。
* **境界値分析（Boundary Value Analysis）：** $n, n-1, n+1$ などの「境目」を特定し、不具合の起きやすいポイントを重点的に検証せよ。
* **デシジョンテーブル（Decision Table）：** 複数の条件が絡む仕様に対し、組み合わせ漏れがないよう表形式で整理せよ。
* **状態遷移テスト（State Transition Testing）：** 許可される遷移だけでなく、仕様上禁止されている不正な遷移（例：完了後から仮予約への戻り）も検証せよ。
* **エラー推測（Error Guessing）：** 二重送信、タイムゾーン、通信失敗、空文字/null混在など、実運用で起きやすい事故パターンを予測してケースに含めよ。

### **2. テスト対象の深掘り**

以下のポイントが漏れていないか、常にチェックせよ。

* 境界条件の処理
* 条件分岐の全組み合わせ
* 不正な状態遷移のブロック
* 例外系・失敗時の挙動
* API側でのバリデーション（フロントエンドとの二重守備）

## **Standard Workflow**

AIがテストを生成する際は、以下のステップを厳守せよ。

1. **解析（Analyze）：** 対象のコードまたは仕様を読み込み、複雑性を把握せよ。
2. **設計（Design）：** コードを書く前に、同値分割・境界値・デシジョンテーブル等を用いて「テスト観点リスト」を先に提示せよ。
3. **レビュー（Review）：** 提示した観点に「実運用上のリスク（二重送信、権限不足等）」が含まれているか確認せよ。
4. **実装（Implement）：** 合意された観点に基づき、具体的なテストコードを生成せよ。

## **Instruction Templates**

ユーザーからテスト作成を依頼された場合、以下の思考プロセスで回答せよ。

* **ステップ1（整理）：** 「以下のQA技法に基づき、テスト観点を整理しました」と報告し、ケースを列挙せよ。
* **ステップ2（確認）：** 「この観点で不足がないか確認してください」とユーザーに促せ。
* **ステップ3（生成）：** 確定した観点を元に、保守性の高いテストコードを出力せよ。

## **Checklist Based Quality Control**

出力前に以下のチェックリストを自問せよ。

* [ ] 正常系だけで満足していないか？
* [ ] 境界値（0, 1, 最大値, 最大値+1等）を含めたか？
* [ ] 異常系やAPIエラー時の挙動をカバーしたか？
* [ ] 条件の組み合わせに漏れはないか？
* [ ] 二重送信や不整合など、実運用上の事故パターンを考慮したか？
